# bot-detect — classificador v1

- **Bot:** bot-detect (SCRUM-4) — classifica se um número que conversa com o nosso bot é
  **outro bot/empresa** ou um **cliente humano real**.
- **Modelo:** o configurado em runtime (PR-C lê de config; ex. `gpt-4o-mini` na zona-cinza,
  escalando para `gpt-4o` se necessário). **Persona-free** (sem barbearia/tom).
- **Temperatura:** `0` (classificação determinística).
- **Entrada:** as **últimas N mensagens `human`** (default N=12) do número analisado, em
  ordem cronológica. Só o lado do número (não as respostas `ai` do nosso bot).
- **Saída:** **JSON estrito** `{ is_bot, confidence, reason }`. Sem texto fora do JSON.
- **Quando roda:** SÓ na **zona-cinza** do pipeline híbrido (ver `docs/bot-detect/sinais.md`).
  Casos óbvios são resolvidos por heurística barata, sem LLM.

> ⚠️ Esta PR é **só design**. O prompt não está fiado em runtime; PR-C/PR-D consomem.

## System prompt (v1)

```
Você é um classificador. Sua única tarefa é decidir se as mensagens abaixo foram
escritas por um SER HUMANO real (cliente) ou por um BOT/sistema automatizado/empresa
de marketing.

Contexto: as mensagens chegaram a um atendimento automatizado de WhatsApp de uma
barbearia/PME brasileira. Clientes humanos escrevem de forma curta, informal, com
gírias e erros de português, perguntas simples (ex.: marcar horário, preço, "tem vaga?"),
áudios, e cadência irregular. Bots/empresas mandam texto com formatação de marketing
(negrito com asteriscos, blocos de emoji, links, CTAs como "clique", "junte-se",
"promo", "sorteio"), mensagens repetidas/templated, e respondem de forma regular.

Sinais de BOT: formatação de campanha, links/CTAs, texto idêntico repetido, tom de
marca/empresa, frases genéricas de divulgação, ausência total de gíria/erro humano.
Sinais de HUMANO: mensagens curtas e informais, gíria e erro de PT-BR, perguntas
diretas sobre agendamento/preço, referência a áudio, variação natural.

REGRAS:
- Responda APENAS com um objeto JSON válido, nada antes ou depois.
- Formato EXATO: {"is_bot": boolean, "confidence": number, "reason": string}
- "confidence" é de 0 a 1 (sua certeza na classificação, não a probabilidade de ser bot).
- "reason" é curto (1 frase, em pt-BR), citando o sinal decisivo.
- Na dúvida genuína, prefira is_bot=false com confidence baixa — marcar um cliente real
  como bot é o erro mais caro.
- NÃO invente conteúdo; julgue só pelas mensagens dadas.
```

## User message (montado em runtime pelo PR-C)

```
Mensagens do número (cronológico, só o lado dele):
1. <msg human 1>
2. <msg human 2>
...
N. <msg human N>

Classifique.
```

> O PR-C injeta as mensagens já mascaradas (sem telefone/PII em claro além do conteúdo
> da própria mensagem). N default = 12; truncar mensagens longas.

## Schema de saída (zod) — doc/snippet, NÃO wired em runtime

O PR-C deve validar a saída com este schema antes de confiar no veredito. Se o parse
falhar (modelo devolveu texto extra / JSON inválido), o pipeline trata como **HUMANO**
(default seguro) e loga o erro — nunca pausa por saída malformada.

```ts
import { z } from 'zod';

export const botDetectResultSchema = z.object({
  is_bot: z.boolean(),
  confidence: z.number().min(0).max(1),
  reason: z.string().min(1).max(280),
});

export type BotDetectResult = z.infer<typeof botDetectResultSchema>;

// Limiar de decisão (alinhado à regra dura de sinais.md):
//   marca bot por LLM só se is_bot === true && confidence >= 0.85
export const BOT_DETECT_LLM_CONFIDENCE_THRESHOLD = 0.85;
```

## Observabilidade exigida (PR-C)

Por chamada, logar: `model`, `input_tokens`, `output_tokens`, `latency_ms`, `slot`,
`phone` (mascarado), `is_bot`, `confidence`. Custo é input-dominado; só a zona-cinza paga.

## Padrões obrigatórios (PR-C ao fiar em runtime)

- timeout 30s; retry idempotente 3× com backoff; fallback de provider (DeepSeek ↔ OpenAI).
- temperatura **0** explícita.
- saída validada pelo zod acima; parse-fail ⇒ trata como humano.
